# Hardware telemetry: measured signals, separate from estimates

The **Hardware and memory** Grafana dashboard has twelve panels. Process metrics come from a two-second sampler in the gateway and each worker; no privileged host mount is needed. The Hardware UI shows only the gateway process. All metrics below are measured, never generated by the GPU planning calculator.

| Signal | Metric | Unit / interpretation |
|---|---|---|
| Process CPU | `rate(lab_resource_process_cpu_seconds_total[1m])` | Cores consumed; 1.0 = one fully busy logical core |
| Latest CPU interval | `lab_resource_process_cpu_cores` | Two-second interval, absent on first sample |
| Resident memory | `lab_resource_process_rss_bytes` | Process RAM bytes, not GPU memory |
| Host RAM available | `lab_resource_host_memory_available_bytes` | Host-visible estimate; do not sum across containers on the same host |
| Container memory | `lab_resource_cgroup_namespace_root_memory_current_bytes` / `...memory_limit_bytes` | Namespace-root cgroup-v2 current/limit; a limit may be unavailable or unlimited |
| CPU quota | `lab_resource_cgroup_namespace_root_cpu_quota_cores` | Local quota/period, not effective CPU count |
| CPU throttling | `rate(lab_resource_cgroup_namespace_root_cpu_throttled_seconds_total[5m])` | Throttled seconds per wall second, not normalized utilization |
| Collection health | `lab_resource_sample_available`, `lab_resource_sample_age_seconds` | Missing/stale samples must not be interpreted as idle hardware |

The cgroup reader assumes Docker's private cgroup namespace. It does not resolve ancestor limits, cpusets, cgroup v1 or arbitrary native-process cgroup paths. Separate resource alerts cover local container memory pressure, sustained CPU throttling and missing/stale samples. Alert evaluation is configured; notification delivery still needs your chosen receiver.

## Optional real GPU exporter

No GPU exporter or GPU instance starts automatically. On an explicitly provisioned compatible NVIDIA GPU host:

1. Install a pinned, driver-compatible [NVIDIA DCGM Exporter](https://docs.nvidia.com/datacenter/dcgm/latest/installation/install-dcgm-exporter.html). Review host privileges; do not add broad privileges to CPU lab containers.
2. Use `observability/dcgm-fields.csv` as the exporter's collector file: `dcgm-exporter -f /path/to/dcgm-fields.csv`. Check supported profiling fields on that GPU. If unsupported, omit profiling rows and leave those panels unavailable.
3. Make port 9400 reachable **only** from Prometheus over a private network or tunnel. A loopback-only exporter needs a same-host scraper or a tunnel; a private-IP target cannot reach another host's loopback listener.
4. Populate `observability/gpu-targets.json` with private addresses, for example:

```json
[{"targets":["10.0.0.10:9400"],"labels":{"role":"prefill"}},
 {"targets":["10.0.0.11:9400"],"labels":{"role":"decode"}}]
```

For a same-host two-GPU exporter, use one target with `role: shared-host`; distinguish devices with the exporter-provided `gpu`/UUID labels. Do not label the entire exporter as a single serving role if it covers both.

Prometheus file discovery picks up targets automatically. The default empty file yields no GPU data. Failed configured scrapes show `up{job="gpu-hardware"} == 0`; no data is not zero usage. Panel validity guards suppress common sentinel/out-of-range values.

| GPU signal | Meaning |
|---|---|
| `DCGM_FI_DEV_FB_USED` | Framebuffer used in MiB; dashboard multiplies by 1048576 for bytes. Includes more than KV; VRAM is not necessarily HBM. |
| `DCGM_FI_DEV_GPU_UTIL` | Coarse GPU activity percentage, not achieved FLOP/s. |
| `DCGM_FI_PROF_DRAM_ACTIVE` | Fraction of cycles with device-memory activity—not GB/s or measured fraction of peak bandwidth. |
| `DCGM_FI_PROF_SM_ACTIVE` | SM activity fraction; active warps can be waiting for memory. |
| `vllm:kv_cache_usage_perc` | Engine KV-pool utilization, not total GPU-memory utilization. Comes from the separate engine target. |

Use DCGM to identify candidate bottlenecks, then correlate with engine prefill/decode metrics and request traces. [NVIDIA's profiling guide](https://docs.nvidia.com/datacenter/dcgm/latest/learn/modules/profiling.html) explains metric limitations and profiler conflicts. Sampled device metrics do not attribute resources to individual requests. Do not infer real HBM bandwidth by multiplying DRAM activity by a spec-sheet bandwidth.

## Follow a symptom across layers

| Symptom | Check first | Then test |
|---|---|---|
| High TTFT, low GPU activity | Gateway/worker queues, CPU throttling, tokenization or transfer delay | Reduce concurrency, inspect traces, verify engine receives work |
| Slow decode, memory activity high | End-context length, batch size, engine ITL and GPU DRAM/SM activity | Compare shorter contexts and supported precision at equal hardware |
| GPU memory nearly full | Total VRAM versus the engine's KV pool and model allocation | Reduce active sequences/context; test admission limits |
| Container near RAM limit | RSS versus cgroup current; host available RAM separately | Inspect buffers, page cache, retention and optional offload |
| Missing GPU values | Empty target file, failed scrape, unsupported profiling field | Restore telemetry; do not call missing values “idle” |

These are investigation paths, not automatic causal diagnoses. The CPU simulator cannot validate GPU bottlenecks.

## Reproducible planning evidence

`POST /api/hardware/estimate` returns `source=analytical_estimate`, full inputs, assumptions, byte accounting, a bounded context sweep and optimistic performance bounds. It produces no GPU metrics. `GET /api/hardware/resources` returns `source=measured` and null/unavailable fields when appropriate. Both use the lab bearer key. See the [model contract](hardware-memory.md).
